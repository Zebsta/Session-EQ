# Сборка и релизы

## Сборка из исходников

Нужны JDK 17, Android SDK platform 35 и build-tools 35.0.0.
Gradle Wrapper 8.10.2 включён в репозиторий. У приложения нет сторонних
библиотек времени выполнения.

Укажи SDK через `ANDROID_HOME` или локальный, не отслеживаемый Git файл
`local.properties` в корне проекта:

```properties
sdk.dir=/absolute/path/to/android-sdk
```

Linux/macOS:

```sh
./gradlew verifyCore :app:assembleDebug
```

Windows:

```powershell
.\gradlew.bat verifyCore :app:assembleDebug
```

Результат: `app/build/outputs/apk/debug/app-debug.apk`.
GitHub Actions выполняет эти же проверки и сохраняет отладочный APK как артефакт.
Для установки опубликованных версий используй [Releases](https://github.com/Zebsta/Session-EQ/releases).

`verifyCore` проверяет математику EQ, Rock со скриншота, хранение сессий,
разбор обоих форматов аудиодампов, исключение AIMP и правила автоподключения.
Реальное звучание, работа Android-службы и расход батареи проверяются на устройстве.

## Сборка APK с постоянной подписью

В Linux доступен `./build.sh`. Он использует `SESSION_EQ_SDK`, `ANDROID_HOME`
или `ANDROID_SDK_ROOT`; результат попадает в `dist/Session-EQ-VERSION.apk`.

Ключ задаётся через `SESSION_EQ_SIGNING_KEY`. Текущий сценарий рассчитан на
ключ разработки с alias `androiddebugkey` и паролем `android`; значение по
умолчанию — `~/.local/share/session-eq/debug.keystore`, вне репозитория.
Опубликованные ранние APK используют один и тот же ключ разработки, чтобы
сохранялась возможность обновления существующих установок.

Ключи, их резервные копии, APK, SDK-пути и дампы телефона не коммитятся.
Отладочная подпись GitHub Actions отличается от подписи опубликованных APK:
артефакт CI может не установиться поверх версии из Releases.

## Порядок публикации

1. Изменения проходят PR в `main` и проверку `build` в GitHub Actions.
2. Версия и versionCode должны совпадать в `app/build.gradle` и манифесте;
   версия в окне «О приложении» также обновляется. versionCode увеличивается.
3. Собери APK, проверь его версию, подпись и возможность обновления.
4. Создай аннотированный тег `vX.Y.Z` на коммите исходников этой версии.
5. Опубликуй GitHub Release с APK, описанием изменений и `SHA256SUMS`.
   В контрольных суммах используй имя файла без локального пути `dist/`.
6. Обнови ссылку загрузки в README и историю изменений.

Теги релизов сохраняют точные версии исходников. Не перемещай опубликованные
теги и не заменяй APK под тем же номером версии другим файлом.

Архивные теги `archive/*` сохраняют отложенные эксперименты. Они не являются
релизами и не предназначены для установки.
